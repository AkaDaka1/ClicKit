# Security policy · Политика безопасности

> **English summary.** Please report vulnerabilities privately via GitHub
> Security Advisories (the "Report a vulnerability" button on the Security tab),
> not in public issues. This is a solo-maintained hobby project: reports are
> acknowledged on a best-effort basis, usually within 7 days. The latest 1.0.x
> release is supported.

## Поддерживаемые версии

| Версия | Поддержка |
|---|---|
| `1.0.x` | ✅ Исправления безопасности выпускаются |
| Старше `1.0` | ❌ Не поддерживаются (development-снимки до релиза) |

Сервис ClicKit Cloud (каталог `service/`) развивается в рамках `master` и не
имеет отдельного публичного релиза; исправления выходят вместе с очередным
коммитом/образом.

## Как сообщить об уязвимости

**Не открывайте публичный issue.** Используйте приватный канал GitHub:

- вкладка **Security** репозитория → **Report a vulnerability**
  ([прямая ссылка](https://github.com/AkaDaka1/ClicKit/security/advisories/new));
- либо напишите мейнтейнеру через GitHub, если форма недоступна.

Пожалуйста, приложите:

- версию ClicKit (`Помощь → О программе`) и версию Windows;
- способ запуска (архив `ClicKit-win64.zip`, `python -m app`, контейнер);
- шаги воспроизведения и ожидаемое/фактическое поведение;
- фрагмент журнала `%APPDATA%\ClicKit\logs\app.log` **без** персональных данных
  и секретов (пути можно заменить на `<пользователь>`).

Проект поддерживается одним человеком, поэтому сроки — по возможности:
подтверждение получения в течение **7 дней**, дальше — согласованный план
исправления и раскрытия. Публичное раскрытие — после выхода исправления.

## Что считается уязвимостью

**Desktop-приложение (`app/`, `core/`, `gui/`, `bridge/`):**

- исполнение произвольного кода из файла сценария `.acl.json` или из
  Blockly-холста (формат IR должен исполнять только известные узлы);
- обход валидации IR (глубина/количество узлов, типы, координаты) с падением
  или зависанием приложения;
- утечка содержимого журнала/настроек в файл сценария, диалог или сеть;
- эскалация возможностей эмуляции ввода за пределы заявленного поведения
  (клики, клавиши, колесо) — например, выполнение shell-команд.

**Сервис (`service/`, `cloud/`, `docker/Dockerfile.service`):**

- обход авторизации `X-API-Key` или разделения ролей write/admin;
- выполнение произвольного кода/SSRF/SQL-инъекция через тела запросов;
- утечка секретов (`CLICKIT_API_KEY`, `POSTGRES_PASSWORD`) в ответы, журналы
  или образ;
- отказ в обслуживании через обход лимита тела запроса (1 МБ) или валидации;
- попадание персональных данных в crash-отчёты (санитайзер home-путей).

## Что уязвимостью не считается

- **Предупреждение SmartScreen.** Сборки не подписаны коммерческим
  сертификатом — это известное ограничение, а не дефект безопасности.
- **Нарушение правил игры/сервиса** при использовании автокликера —
  ответственность пользователя, см. дисклеймер в [`README.md`](README.md).
- **Локальные настройки и журналы** — файлы в `%APPDATA%` доступны тому, у кого
  уже есть доступ к учётной записи Windows; это не модель угроз проекта.
- **Отсутствие HTTPS на локальном compose** (`docker-compose.cloud.yml`) —
  локальная разработка; публичный TLS-контур запланирован в M9.

## Меры, уже заложенные в проект

- API-ключи только из переменных окружения; без `CLICKIT_API_KEY` сервис не
  стартует (fail-closed), ключи сравниваются `hmac.compare_digest` и не
  попадают в ответы и журналы.
- IR валидируется единой схемой `core/ir/schema.py`; произвольный код из
  Blockly не исполняется, страница редактора не имеет доступа к сети.
- Тело запроса ограничено 1 МБ до разбора JSON; ошибки отдаются в RFC 7807
  без внутренних деталей, `request_id` связывает ответ и журнал.
- Crash-отчёты проходят санитайзер: домашние каталоги заменяются на
  `<пользователь>`, traceback обрезается до 16 КБ, тело отчёта не логируется.
- Плановые ворота безопасности (Dependabot, pip-audit, Trivy, CodeQL,
  gitleaks, SBOM, cosign) зафиксированы в `plans/M11-security-resilience.md`.
