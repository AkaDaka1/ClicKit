# Шаблон blameless-постмортема

> Скопируйте файл в `docs/sre/postmortems/ГГГГ-ММ-ДД-<slug>.md` в момент
> инцидента (не после), заполните по мере разбора и удалите этот блок.
> Полный пример — [`postmortems/2026-10-29-release-pipeline.md`](postmortems/2026-10-29-release-pipeline.md).

## Правила

1. **Blameless.** Разбираем систему и решения, а не людей. «Забыл проверить»
   — это не причина; причина — почему проверка была необязательной или
   незаметной.
2. **Факты и время.** Каждая строка таймлайна — с временем UTC и источником
   (ссылка на прогон CI, `request_id`, скриншот, строка журнала). «Примерно
   в обед» — не время.
3. **Причины, а не виноватые.** Одна основная причина + способствующие
   факторы. Если причин несколько, они перечисляются отдельно.
4. **Действия с владельцем и сроком.** «Быть внимательнее» — не действие.
   Действие меняет систему: тест, алерт, шаг пайплайна, документ.
5. **Срок.** Черновик — в день инцидента, разбор — в течение 3 рабочих дней.
6. **Публичность внутри проекта.** Постмортем лежит в Git рядом с кодом: он
   часть инженерной памяти, а не переписка.

## 1. Краткое резюме

Три–пять предложений: что произошло, кто и как заметил, что сделали, чем
закончилось. Читатель должен понять суть, не открывая остальное.

## 2. Таймлайн

Время — UTC (в скобках можно MSK). Источник — ссылка/ID.

| Время | Событие | Источник |
|---|---|---|
| 00:00 | первое отклонение (алерт, красный прогон, жалоба) | |
| 00:00 | обнаружение: кто/что заметил | |
| 00:00 | начало реакции | |
| 00:00 | первая гипотеза и проверка | |
| 00:00 | смягчение (mitigation) | |
| 00:00 | восстановление (resolved) | |
| 00:00 | закрытие инцидента | |

## 3. Влияние

- **Пользователи:** кто, сколько, что видели (отказ, 500, медленно).
- **Данные:** были ли потеряны/повреждены, как проверено.
- **SLO:** какой SLI, за какой период, сколько минут/процентов бюджета.
- **Доставка:** задержка релиза, пропущенные артефакты, неверная версия.
- **Что не пострадало** — тоже полезно: границы влияния.

## 4. Причины

### 4.1. Основная причина

Одно-два предложения, описывающее механизм отказа: «X ожидал Y, а система
производила Z, потому что …».

### 4.2. Способствующие факторы

- почему ошибку не поймали раньше (тест, проверка, алерт);
- почему среда отличалась (локально/CI, версия, остатки файлов);
- почему восстановление заняло столько времени.

### 4.3. Пять «почему»

1. Почему …? — Потому что …
2. Почему …? — Потому что …
3. …

Остановитесь, когда следующий ответ — «потому что так исторически сложилось»:
это и есть системная причина, с ней и работают действия.

## 5. Обнаружение и реакция

| Вопрос | Ответ |
|---|---|
| Как узнали? (алерт / CI / пользователь) | |
| Сколько прошло от начала до обнаружения | |
| Что помогло диагностировать | метрика / лог / трейс / diff |
| Что мешало | нет алерта / нет лога / непонятная ошибка |
| Сработал ли runbook | да/нет, какой сценарий, где ошибся |

## 6. Действия

| ID | Действие | Тип | Владелец | Срок | Статус |
|---|---|---|---|---|---|
| A1 | | prevent / detect / mitigate / document | | | |

- **prevent** — убирает причину (тест, контракт, проверка);
- **detect** — ускоряет обнаружение (алерт, метрика, лог);
- **mitigate** — сокращает время восстановления (runbook, откат, healthcheck);
- **document** — закрепляет знание.

Действия без владельца и срока не считаются выполненными.

## 7. Уроки

Что теперь знаем, чего не знали до инцидента. Формулировки — проверяемые:
«локальные прогоны не воспроизводят чистую среду CI», а не «нужно быть
аккуратнее».

## 8. Приложения

- ссылки на прогоны CI, коммиты, PR;
- `request_id`/`trace_id` проблемных запросов;
- выдержки журналов (без ключей и PII);
- скриншоты дашборда/Grafana;
- дампы `promtool`/тестов, если релевантно.

## 9. Чек-лист завершения

- [ ] Таймлайн заполнен фактами со ссылками, время в UTC.
- [ ] Указаны влияние на SLO и израсходованный бюджет.
- [ ] Причина сформулирована как механизм, а не как «человек ошибся».
- [ ] У каждого действия есть владелец, срок и тип.
- [ ] Runbook/алерты/тесты обновлены там, где они не сработали.
- [ ] Постмортем прочитан и принят; статус — `готов`.
