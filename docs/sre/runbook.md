# Runbook: что делать, когда сработал алерт

> Статус: принято 2026-11-21 (M8 T3.2). Runbook — рабочая инструкция, а не
> эссе: его читают в момент инцидента, с телефона, без доступа к исходникам.
> Пороги и формулы здесь **не дублируются** — единственный источник истины
> [`slo.md`](slo.md) и правила `observability/prometheus/alerts.yml`.
> Разбор инцидента после — по [`postmortem-template.md`](postmortem-template.md).

## 1. Как пользоваться

1. Найдите сработавший алерт в таблице §2 и откройте его сценарий.
2. Выполните «первые 3 минуты» — это минимальные проверки, которые отделяют
   «сервис лежит» от «врёт метрика».
3. Действуйте по шагам сверху вниз: сначала обратимые действия (рестарт,
   откат), потом изменения кода и данных.
4. Записывайте время каждого шага в UTC — постмортем собирается по таймлайну,
   а не по памяти.

### 1.1. Что нужно под рукой

| Что | Где |
|---|---|
| Стек наблюдаемости | `docker compose -f docker-compose.observability.yml ...` из корня репозитория |
| Дашборд | <http://127.0.0.1:3000/d/clikit-cloud> |
| Активные алерты | <http://127.0.0.1:9090/alerts>, <http://127.0.0.1:9093> |
| Приёмник вебхуков | <http://127.0.0.1:8080/alerts> |
| Журналы API | `docker compose -f docker-compose.observability.yml logs --since 15m api` |
| `request_id` | заголовок `X-Request-ID` ответа или `request_id` в problem+json |

Если стек наблюдаемости не поднят, а сервис запущен отдельно
(`docker-compose.cloud.yml`), меняйте файл в командах на
`docker-compose.cloud.yml`; метрики и алерты при этом недоступны — это уже
повод поднять стек.

### 1.2. Общие правила

- **Сначала сохраните улики, потом перезапускайте.** Если контейнер ещё
  отвечает, снимите `logs`, `docker stats`, `request_id` и `trace_id`
  проблемного запроса. Если не отвечает — сначала рестарт, улики потом:
  восстановление важнее полноты.
- **Один эксперимент за раз.** Не меняйте одновременно образ, конфиг и БД:
  иначе непонятно, что помогло, и постмортем снова будет «по памяти».
- **Заморозка изменений.** При израсходованных ≥ 75 % error budget
  (политика — [`slo.md`](slo.md) §7) релизы и рискованные правки
  останавливаются до восстановления.
- **Не удаляйте данные ради «чистого старта».** `down -v` уничтожает
  `pgdata` и историю наблюдаемости; это крайняя мера с явной записью в
  таймлайне.
- **Инцидент — это когда есть влияние.** Падение пайплайна релиза без
  влияния на работающий сервис — тоже инцидент доставки (сценарий §10), но
  с меньшим приоритетом, чем доступность.
- **После любого `critical`-алерта** пишется постмортем, даже если всё
  починилось за 5 минут.

сами после восстановления.

## 3. `ClikitApiDown` — сервис недоступен

**Признаки.** Prometheus не может скрейпить `clikit-api` (`up == 0`) дольше
минуты; Grafana показывает разрыв графиков; клиенты получают отказ соединения.
SLI этого не видит (запросы не доходят до приложения, [`slo.md`](slo.md) §3),
поэтому это единственный алерт, который ловит полное падение.

**Первые 3 минуты.**

```powershell
docker compose -f docker-compose.observability.yml ps
docker compose -f docker-compose.observability.yml logs --tail=100 api
docker compose -f docker-compose.observability.yml ps db migrate
curl.exe -s -o NUL -w "%{http_code}`n" http://127.0.0.1:8000/healthz
```

**Диагностика.**

1. Контейнер `api` в состоянии `restarting`/`exited` — смотрите последние
   строки журнала: ошибка конфигурации, падение при старте, OOM.
2. Контейнер `api` запущен, но `/healthz` не отвечает — проверьте, что порт
   не занят другим процессом (`CLICKIT_API_PORT`) и что uvicorn слушает
   нужный адрес.
3. `db` не `healthy` — см. §6 и [`cloud.md`](../cloud.md) §9; `/readyz`
   вернёт 503 при живом `/healthz`, это не повод перезапускать API.
4. `migrate` завершился с ошибкой — API не стартует специально (схему меняет
   только Alembic, ADR №52). Смотрите `logs migrate` и §6.

**Действия.**

```powershell
# 1. Мягкий рестарт только API (данные и БД не трогаются)
docker compose -f docker-compose.observability.yml restart api

# 2. Если не помогло — пересоздать контейнер из текущего образа
docker compose -f docker-compose.observability.yml up -d --force-recreate api

# 3. Если сломан сам образ/конфиг — вернуться на предыдущий рабочий коммит
git log --oneline -5
git switch --detach <sha>          # последний зелёный коммит, не рабочая ветка
docker compose -f docker-compose.observability.yml up -d --build api
# после разбора: git switch -   (вернуться в рабочую ветку)
```

Откат миграции — только если она обратима и не теряет данные:

```powershell
# ВНИМАНИЕ: сначала проверьте downgrade на копии БД (docs/cloud.md §8.2).
# ENTRYPOINT сервиса migrate — «upgrade head», поэтому он заменяется целиком.
docker compose -f docker-compose.observability.yml run --rm --entrypoint python `
  migrate -m alembic -c service/alembic.ini downgrade -1
```

**Восстановление.** `up{job="clikit-api"} == 1`, `/healthz` и `/readyz` — 200,
`ClikitApiDown` ушёл в `resolved` (приёмник получил `resolved`), на дашборде
пошёл трафик.

**Не делать.** Не удаляйте том `pgdata` и не выполняйте `down -v`; не
перезапускайте всю БД из-за недоступного API, пока не доказано, что причина
в ней.

## 4. Высокая доля 5xx и быстрый расход бюджета

**Признаки.** `High5xxRate` — доля 5xx > 1 % за 5 минут (ранний сигнал);
`FastErrorBudgetBurn` — расход в 14.4 раза быстрее нормы за час (critical,
~2 % бюджета). 4xx клиента бюджет **не** жгут и в этот сценарий не входят.

**Первые 3 минуты.**

```powershell
# 1. Какие маршруты и статусы дают ошибки
curl.exe -s "http://127.0.0.1:9090/api/v1/query?query=sum%20by%20(route%2Cstatus)%20(rate(clikit_http_requests_total%5B5m%5D))" |
  ConvertFrom-Json | ForEach-Object { $_.data.result } |
  Select-Object @{n='route';e={$_.metric.route}}, @{n='status';e={$_.metric.status}},
                @{n='rps';e={$_.value[1]}}

# 2. Ошибки в журнале за последние 15 минут
docker compose -f docker-compose.observability.yml logs --since 15m api |
  Select-String '"level":"ERROR"' | Select-Object -Last 20
```

В Loki/Grafana: `{service="api"} | json | level="ERROR"`; поле `error_type`
и `request_id` связывают запись с трейсом.

**Диагностика по типовым причинам.**

| Что видно | Вероятная причина | Куда смотреть |
|---|---|---|
| `500` на всех маршрутах сразу | упал процесс/БД, ошибка конфигурации | §3, §6 |
| `500` только на `POST /v1/scenarios` | валидация IR падает исключением, а не 422 | трейс запроса в Tempo, `error_type` |
| `500` на `GET /v1/scenarios/{id}` | ошибка сериализации/БД | трейс + `pg_stat_activity` |
| `503` на `/readyz` | недоступна БД | §6 |
| Массовые `401`/`403` | это **4xx**, бюджет не жгут; проверьте ключи клиента | `docs/cloud.md` §9 |

**Действия.**

1. Найдите первый `request_id` с 500 и откройте трейс в Tempo: спан покажет,
   упал ли запрос на HTTP-слое или в SQL.
2. Если ошибки начались после релиза — откатите релиз (см. §3, шаг 3) до
   выяснения причины; это дешевле, чем разбираться под нагрузкой.
3. Если причина в данных (битый сценарий ломает чтение) — не удаляйте запись
   без бэкапа: снимите дамп (`docs/cloud.md` §8.2), затем разбирайте.
4. Если причина внешняя (БД, диск, память) — переходите в §6–§9.

**Восстановление.** `clikit:http_errors:ratio_rate5m` вернулся к нулю,
`FastErrorBudgetBurn` resolved, burn rate 1 ч ≤ 1. Дальше — решение по
политике бюджета: при ≥ 50 % израсходованного режим «осторожно», при ≥ 75 %
— заморозка ([`slo.md`](slo.md) §7).

## 5. Высокая задержка сценариев

**Признаки.** p95 успешных запросов к `POST /v1/scenarios` и
`GET /v1/scenarios/{id}` выше 300 мс дольше 10 минут. Пользователь видит
медленную публикацию/скачивание, ошибок может не быть вовсе.

**Первые 3 минуты.**

```powershell
# p95 по порогу SLO (общая запись для алерта и разбора)
curl.exe -s "http://127.0.0.1:9090/api/v1/query?query=clikit:sli_latency:p95_rate5m" |
  ConvertFrom-Json | ForEach-Object { $_.data.result } |
  Select-Object @{n='p95_s';e={$_.value[1]}}

# Долгие запросы в PostgreSQL
docker compose -f docker-compose.observability.yml exec db psql -U clikit -d clikit `
  -c "SELECT pid, state, wait_event_type, now() - query_start AS age, left(query, 120) AS query FROM pg_stat_activity WHERE datname = 'clikit' AND state <> 'idle' ORDER BY age DESC LIMIT 10;"
```

**Диагностика.**

1. Медленные спаны SQL в Tempo: записи `p95` не хватает, чтобы понять
   *какой* запрос тормозит, — откройте трейс по `trace_id` из журнала
   медленного запроса и найдите самый долгий дочерний спан SQL. Текст SQL в
   спаны намеренно не пишется (ADR №63), поэтому запрос сопоставляется с
   `pg_stat_activity` по времени и `pid` из журнала.
2. Пул БД: `clikit_db_pool_connections{state="in_use"}` близок к 5 — см. §6.
3. Рост трафика: `clikit:http_requests:rate5m` — если вырос в разы, это
   нагрузка, а не регрессия; проверьте, не долбит ли клиент без паузы.
4. Хост: CPU/RAM на дашборде; при нехватке памяти — §7.
5. VACUUM/autovacuum: `pg_stat_activity` с `wait_event_type = 'IO'` и
   `state = 'active'` на большом `scenarios`.

**Действия.**

1. Сначала устраните причину (пул, память, медленный запрос), не
   перезапускайте API «на всякий случай».
2. Если задержку даёт один тяжёлый запрос — завершите его только после
   сохранения `query` и плана (`EXPLAIN` на копии), затем повторите.
3. Если это регрессия релиза — откат (§3, шаг 3).
4. Порог SLO не повышайте: сначала измерьте, потом меняйте цифры через ADR
   ([`slo.md`](slo.md) §10).

**Восстановление.** p95 ≤ 300 мс, `HighScenarioLatency` resolved, на
дашборде p50/p95/p99 вернулись к обычному уровню.

## 6. Пул соединений БД исчерпан

**Признаки.** `DbPoolExhausted` — `in_use >= 5` (штатный `pool_size`) дольше
5 минут. Дальше соединения берутся из `max_overflow` (10), после чего запросы
начинают ждать и превращаются в 5xx/латентность.

**Первые 3 минуты.**

```powershell
# Состояния пула: in_use / idle / overflow
curl.exe -s http://127.0.0.1:8000/metrics | Select-String "clikit_db_pool_connections"

# Кто держит соединения
docker compose -f docker-compose.observability.yml exec db psql -U clikit -d clikit `
  -c "SELECT state, count(*) FROM pg_stat_activity WHERE datname = 'clikit' GROUP BY state;"

# Долгие транзакции
docker compose -f docker-compose.observability.yml exec db psql -U clikit -d clikit `
  -c "SELECT pid, state, now() - xact_start AS age, left(query, 100) FROM pg_stat_activity WHERE datname = 'clikit' AND xact_start IS NOT NULL ORDER BY age DESC LIMIT 10;"
```

**Диагностика.**

1. Утечка сессий: `in_use` не падает после окончания запросов — ищите код,
   который не закрывает `session_scope` (в норме — контекстный менеджер
   `repository.py`).
2. Долгая транзакция держит соединение: `idle in transaction` > минуты —
   обычно это забытый `commit`/`rollback`.
3. Медленный запрос блокирует пул: см. §5.
4. Нагрузка выросла — соединений физически не хватает: это повод поднимать
   `pool_size` **после** проверки, что запросы быстрые, а не вместо этого.

**Действия.**

1. Завершите зависшие транзакции точечно:
   `SELECT pg_terminate_backend(<pid>);` — только для `idle in transaction`,
   не для активного полезного запроса.
2. Перезапуск API освобождает пул, но **не** устраняет утечку: после
   рестарта найдите причину, иначе алерт вернётся.
3. Если причина в коде — откат релиза, затем исправление с тестом на
   закрытие сессии.
4. Менять `pool_size`/`max_overflow` — через конфиг и с записью в постмортем,
   а не «на глаз» в бою.

**Восстановление.** `in_use` устойчиво ниже 5, `DbPoolExhausted` resolved,
латентность и 5xx вернулись к норме.

## 7. Мало памяти на Docker-хосте

**Признаки.** `HostMemoryLow` — свободно меньше 10 % памяти дольше 5 минут.
Первый симптом для пользователя — рост задержек и `OOMKilled` контейнеров,
поэтому действовать нужно до появления 5xx.

**Первые 3 минуты.**

```powershell
# Кто ест память
docker stats --no-stream

# Что было убито ядром
docker compose -f docker-compose.observability.yml ps -a
docker inspect --format "{{.Name}} restarts={{.RestartCount}} oom={{.State.OOMKilled}}" `
  (docker compose -f docker-compose.observability.yml ps -q)
```

**Диагностика.**

1. Стек наблюдаемости сам занимает ~2 ГБ (лимиты в compose): при нехватке
   памяти на ноутбуке — это ожидаемая причина, а не утечка сервиса.
2. Рост памяти API со временем — утечка (трейсы/сессии); смотрите память
   контейнера `api` в `docker stats` и число спанов.
3. `OOMKilled: true` у контейнера — жертва, а не обязательно виновник.

**Действия.**

1. Остановите лишнее: второй стек/тестовые контейнеры (`docker ps`). Если нужен
   только сервис — оставьте его, убрав стек наблюдаемости:
   `docker compose -f docker-compose.observability.yml stop prometheus grafana loki promtail tempo alertmanager alert-sink node-exporter`
   (полный `down` тоже освобождает память, но останавливает и API с БД).
2. Перезапустите контейнер-жертву:
   `docker compose -f docker-compose.observability.yml up -d --force-recreate <service>`.
3. Если не хватает физически — уменьшите лимиты стека или поднимите память
   хоста; это изменение инфраструктуры, а не «фикс» сервиса.
4. Не отключайте node-exporter: без него алерт исчезнет, а проблема нет.

**Восстановление.** Свободная память > 10 %, `HostMemoryLow` resolved,
контейнеры не перезапускаются, `restarts` не растёт.

## 8. Медленный расход error budget

**Признаки.** `SlowErrorBudgetBurn` — burn rate за 6 часов > 6 (warning, ~5 %
бюджета за окно). Острых ошибок нет, но тренд съедает месяц.

**Что делать.**

1. Посмотрите 6-часовой тренд 5xx и латентности на дашборде; найдите маршрут
   и время начала деградации.
2. Сверьте с журналом: `{service="api"} | json | level="ERROR"` за 6 часов,
   сгруппируйте по `error_type` (Grafana → Explore).
3. Если деградация началась после релиза — откат; если постепенная
   (данные/объём) — тикет на исправление, а не срочный рестарт.
4. Проверьте остаток бюджета: панель доступности за 30 дней. При ≥ 50 % —
   режим «осторожно», при ≥ 75 % — заморозка ([`slo.md`](slo.md) §7).

**Восстановление.** Burn rate 6 ч ≤ 1–2, тикет на причину создан, решение по
бюджету записано.

## 9. Диск и тома заполнены

Отдельного алерта в T3.1 нет (честное ограничение: диск — не SLI сервиса),
поэтому симптом замечается вручную или по косвенным признакам: 5xx от БД,
ошибки записи в журнале, «No space left on device».

**Первые 3 минуты.**

```powershell
docker system df -v
docker compose -f docker-compose.observability.yml ps
docker compose -f docker-compose.observability.yml exec db df -h /var/lib/postgresql/data
```

**Диагностика и действия.**

1. Тома наблюдаемости (`prometheus-data` 40 дней, `loki-data` 30 дней,
   `tempo-data` 14 дней) и `pgdata` — основные потребители.
2. Освободите место **без потери данных**: `docker image prune`,
   `docker builder prune` (кэш сборок), старые `dist/` артефакты.
3. Не удаляйте `pgdata` и не делайте `down -v`: сначала дамп
   (`docs/cloud.md` §8.2), потом решение.
4. Если место кончилось на томе БД — остановите API, освободите место,
   проверьте `pg_isready` и целостность (`pg_dump` в файл), затем поднимайте.
5. Долгосрочно: уменьшить retention или вынести тома на больший диск —
   через ADR, а не правкой в UI.

**Восстановление.** Свободное место есть, БД принимает записи, API отвечает
200, ошибок «No space left on device» в журналах нет.

## 10. Пайплайн релиза упал (инцидент доставки)

Это не алерт наблюдаемости, но штатная операция: релиз не вышел, сервис при
этом может быть жив. Порядок:

1. Откройте упавший прогон `Release` и найдите **первый** упавший job.
   Зелёные job после него — не доказательство исправности.
2. Прочитайте `##[error]` и последние 30 строк шага: типовая причина —
   путь к артефакту, версия/тег, окружение.
3. Воспроизведите шаг локально, **на чистом каталоге** (без остатков `dist/`):
   именно остатки от предыдущих сборок дают «локально зелёно, в CI красно».
4. Исправляйте одной правкой на коммит и перезапускайте; фиксируйте время.
5. После публикации проверьте ассеты релиза (`gh release view <tag>`) и
   SHA-256, а не только зелёный job.

Реальный разбор такого инцидента (три красных прогона 2026-10-29) —
[`postmortems/2026-10-29-release-pipeline.md`](postmortems/2026-10-29-release-pipeline.md).
Урок оттуда: контракт «кто кладёт файл — кто его ищет» должен проверяться
тестом, а не совпадением.

## 11. Политика бюджета: заморозка и нарушение SLO

Срабатывают `ErrorBudgetFreeze` (израсходовано ≥ 75 % бюджета за 30 дней,
warning) и `ErrorBudgetExhausted` (≥ 100 %, critical). Это не про текущую
минуту, а про месяц: сервис может прямо сейчас отвечать нормально, но отпуск
бюджета уже потрачен. Пороги и режимы — [`slo.md`](slo.md) §7.

**Признаки.** Алерт в Prometheus/Alertmanager; на дашборде панель «Остаток
бюджета, мин» близка к нулю (216 мин — целый бюджет); вывод
`python scripts/slo_report.py` показывает режим `freeze` (код 1) или
`exhausted` (код 2).

**Первые 3 минуты.**

```powershell
# 1. Отчёт и код выхода: 0 — normal/careful, 1 — freeze, 2 — exhausted, 3 — нет данных
python scripts/slo_report.py
python scripts/slo_report.py --json

# 2. Из чего сложился расход: 5xx по маршрутам и времени
curl.exe -s "http://127.0.0.1:9090/api/v1/query?query=clikit:http_errors:ratio_rate5m" |
  ConvertFrom-Json | ForEach-Object { $_.data.result }

# 3. Кто именно ошибался — JSON-логи API за сутки
#    Grafana → Explore → Loki: {service="api"} | json | level="ERROR"
```

**Действия.**

1. Найдите источник расхода: инцидент, серия перезапусков, релиз с ошибками
   или плановые работы (они тоже жгут бюджет — §7 правила 1).
2. `freeze` (75–100 %): остановите рискованные релизы и правки, влияющие на
   5xx и латентность; разрешены только исправления надёжности. План
   восстановления бюджета опишите в тикете.
3. `exhausted` (≥ 100 %): SLO нарушен — откройте blameless-постмортем по
   [`postmortem-template.md`](postmortem-template.md) сразу, а не «когда
   будет время»; приоритет всех работ — надёжность.
4. Не пересматривайте цифры SLO, чтобы «покраснеть в зелёный»: изменение
   99.5 %/300 мс/порогов допустимо только через ADR ([`slo.md`](slo.md) §10).
5. 4xx к бюджету отношения не имеют: подбор ключей и битый JSON лечатся в
   клиенте и поддержке, а не заморозкой.

**Восстановление.** `slo_report.py` возвращает 0 (режим `normal` или
`careful`), `ErrorBudgetFreeze`/`ErrorBudgetExhausted` исчезли из
`/api/v1/alerts`, заморозка снята не по календарю, а по факту восстановления
бюджета; для `exhausted` — постмортем создан и действия имеют владельцев.

## 12. Как объявить инцидент и закрыть его

Для пет-проекта «объявить инцидент» — значит зафиксировать это в трёх местах:

1. **Время начала** (UTC) и сработавший алерт — первой строкой будущего
   постмортема.
2. **Статус в репозитории:** создать файл
   `docs/sre/postmortems/ГГГГ-ММ-ДД-<slug>.md` из шаблона сразу, а не после.
3. **Заморозка:** при critical-алерте или израсходованных ≥ 75 % error
   budget — никаких релизов до восстановления (§11).

Закрытие:

- алерт в `resolved`, SLI/burn rate вернулись к норме;
- причина устранена, а не замаскирована (рестарт без понимания — не закрытие);
- действия из постмортема имеют владельца и срок;
- шаблон и этот runbook обновлены, если шаг оказался неверным.

## 13. Проверка runbook

Runbook — такой же код, как правила алертов: он проверяется намеренной
поломкой.

- **T5.1:** демо «сломай и почини» — `stop api` → `ClikitApiDown` firing →
  действия §3 → resolved; сценарий воспроизводится с чистой машины.
- **M11:** chaos-эксперименты (БД, диск, сертификат) проверяют сценарии
  §6–§9 и учебный инцидент.
- **Статические тесты:** `tests/service/test_runbook.py` следят, что у
  каждого алерта есть сценарий, что в документе ≥ 5 сценариев, что ссылки
  не битые, а секретов нет.
