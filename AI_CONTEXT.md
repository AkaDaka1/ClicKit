## 1. Суть проекта

**ClicKit** (рабочее название репозитория до ребрендинга — AutoClicker) —
удобный и красивый автокликер для Windows с визуальным блочным
программированием в стиле Scratch / Blockly.

### Проблема аналогов
- Обычные автокликеры умеют только спамить кликами в одной точке.
- Продвинутые приложения со сценариями имеют сложный, перегруженный и
  недружелюбный интерфейс.

### Наше решение
Понятный UI, где сценарии кликов, перемещений мыши и задержек собираются из
наглядных визуальных блоков кода путём перетаскивания и комбинирования.
Два режима работы:
1. **«Простой режим»** — классический автокликер (интервал, кнопка, повторы) для тех, кому не нужны сценарии.
2. **«Режим сценариев»** — визуальный редактор блоков (Blockly) для сложных последовательностей.

### Целевая аудитория
Геймеры и обычные пользователи Windows, не имеющие навыков программирования.

## 2. Стек технологий

| Слой | Технология | Комментарий |
|---|---|---|
| Язык | Python 3.11+ | Типизация обязательна |
| GUI | **PySide6** | Выбран вместо PyQt6 из-за лицензии LGPL (без ограничений для проприетарного использования) |
| Визуальное программирование | Blockly + `QWebEngineView` | Blockly — локально (vendored в `resources/`), без CDN |
| Мост JS ↔ Python | `QWebChannel` | Обмен JSON между Blockly и движком |
| Эмуляция ввода | `pyautogui` + `pynput` | За абстракцией `InputBackend` (см. архитектуру) |
| Глобальные хоткеи | `pynput` | Слушатель в отдельном потоке |
| Сборка | PyInstaller (позже) | Один .exe для Windows |

## 3. Архитектура

### 3.1. Принципы
- **Слоистость:** GUI ничего не знает об эмуляции ввода; движок ничего не знает о GUI.
- **Потоки:** исполнение сценариев — только в воркере (`QThread`), GUI-поток никогда не блокируется.
- **Безопасность:** глобальный хоткеп аварийного стопа (по умолчанию `F6`) работает всегда,
  даже если сценарий «завис» в цикле.
- **Хоткеи:** `pynput` 1.8+ в `GlobalHotKeys` игнорирует синтетические
  (injected) нажатия — автотесты проверяют только регистрацию/жизненный цикл
  слушателя, реальные `F5`/`F6`/`F8` проверяются вручную (факт выявлен в M1).
- **Один курсор (ограничение Windows):** все устройства ввода, включая
  виртуальные HID-мыши, двигают единственный системный указатель, поэтому
  кликер всегда «занимает» мышь пользователя. «Клики без захвата курсора»
  возможны только как отправка сообщений в целевое окно (`PostMessage`) —
  это отдельный экспериментальный бэкенд (спайк после M2), а не MVP.
- **Скрипт = данные:** сценарий существует в трёх формах:
  `Blockly-JSON → IR (наш внутренний JSON-формат) → последовательность команд движка`.
  GUI/Blockly и движок общаются только через IR.
- **Blockly локально, без сети:** страница `resources/blockly/index.html`
  открывается в `QWebEngineView` из `file://`; Blockly 13.4.0 вендорен и
  обновляется только скриптом `scripts/vendor_blockly.py`. JS ↔ Python —
  исключительно через `QWebChannel`; IR остаётся единственным форматом
  исполнения, состояние холста хранится отдельно в `editor.workspace`.

### 3.3. Ключевые решения (ADR-конспект)
1. **PySide6, а не PyQt6** — лицензия LGPL, официальный Qt for Python, API практически идентичен.
2. **Blockly, а не самописный редактор** — зрелая библиотека drag-and-drop блоков;
   кастомные блоки описываются декларативно (JSON block definitions).
3. **Собственный IR вместо прямого исполнения кода из Blockly** — Blockly может
   генерировать Python-код, но выполнять произвольный код небезопасно и сложно
   отлаживать. IR ограничен нашим набором узлов (клики, движения, задержки, циклы,
   условия), валидируется и исполняется интерпретатором.
4. **Абстракция `InputBackend`** — pyautogui удобен для кликов/перемещений,
   pynput — для слушателей и низкоуровневого контроля; бэкенд выбирается конфигом,
   код движка от бэкенда не зависит.
5. **Название продукта — ClicKit** (2026-10-23, решение пользователя): игра слов
   «click it» + «kit» (набор/конструктор) — отражает суть: сценарии собираются
   как конструктор из блоков. GitHub-репозиторий — `ClicKit`; локальная папка
   будет переименована отдельно. README — двуязычный (EN сверху, RU снизу).
6. **Лицензия проекта — MIT** (2026-10-23, решение пользователя): пермиссивная
   лицензия, разрешающая коммерческое использование и закрытые форки при
   сохранении уведомления об авторских правах. Совместима со всеми зависимостями:
   PySide6/pynput — LGPL v3, Blockly — Apache-2.0, pyautogui — BSD-3-Clause.
   Правообладатель: Danil Momot. Файл `LICENSE` — в корне репозитория; при сборке
   PyInstaller рядом с `.exe` нужно класть NOTICE о LGPL-компонентах Qt.
7. **Единый бэкенд отправки — pyautogui** (2026-10-24, решение с пользователем):
   на Windows и pyautogui, и pynput упираются в один и тот же Win32 API `SendInput`,
   поэтому второй «отправляющий» бэкенд дублирует первый. Абстракция `InputBackend`
   сохраняется ради тестируемости (mock-бэкенд в тестах) и возможности будущего
   raw-input бэкенда для полноэкранных игр (решение — после подтверждения конфликтов,
   см. «Известные проблемы» в `PROGRESS.md`). pynput используется только для
   глобальных слушателей в `core/hotkeys.py`. `pynput_backend.py` исключён из
   структуры (§3.2).
8. **Настройки — JSON в `%APPDATA%\ClicKit\settings.json`** (2026-10-25, M2):
   модель и хранилище в `core/settings.py` без PySide6; запись атомарная
   (временный файл + `os.replace`); битый или отсутствующий файл не роняет
   приложение — берутся дефолты, значения клампятся при загрузке.
   Редактирование хоткеев в UI — M5, но привязки уже читаются из настроек.
9. **Причины завершения исполнения** (2026-10-25, M2): `StopReason`
   (`completed`/`stopped`/`failsafe`/`error`) и `on_finish(reason, detail)`
   в `Executor`. Срабатывание fail-safe pyautogui превращается бэкендом
   в `FailsafeTriggered` и показывается в GUI понятным статусом, а не traceback.
10. **Один `HotkeyManager` + Qt-мост** (2026-10-25, M2): `gui/hotkey_bridge.py`
    регистрирует `F5`/`F6`/`F8` и только эмитит сигналы; чтение виджетов и
    запуск кликов всегда в GUI-потоке (callback pynput живёт в своём потоке).
11. **Executor ↔ GUI только через адаптер** (2026-10-25, M2):
    `gui/executor_adapter.py` (`QObject` + сигналы), `core/` остаётся без
    PySide6. У каждого прогона свой номер: события устаревшего прогона
    отбрасываются, поэтому быстрый «стоп → старт» не сбивает состояние UI.
12. **Платформенное ограничение — один курсор** (2026-10-25, M2): второй
    независимый указатель мыши в Windows невозможен (все устройства сводятся
    к одному курсору). Кликер занимает мышь; аварийный выход — `F6` и `Alt+F4`.
    «Клики без захвата курсора» — только `PostMessage` в целевое окно
    (не для всех приложений), запланировано как спайк после M2 (§3.1, backlog).
13. **Общий потоковый воркер** (2026-10-26, M3): `core/worker.py` —
    `ThreadedWorker` + `StopReason`; запуск/стоп/join/причина завершения
    живут в одном месте. `Executor` (простой режим) и `ScenarioRunner` (IR)
    наследуют его и реализуют только тело прогона. Публичный API `Executor`
    не изменился, `StopReason` реэкспортируется из `core/executor.py`.
14. **IR — версионированный JSON, а не код** (2026-10-26, M3; развитие ADR №3):
    формат `{"version": 1, "name", "nodes": [...]}`, расширение `.acl.json`.
    Узлы: `click`, `double_click`, `move`, `drag`, `delay`, `key`, `scroll`,
    `loop` (`times` — число или `null` = ∞), `sequence`; узел `if`
    **зарезервирован** (разбирается, но интерпретатор отказывает до M4/M5).
    Неизвестный `type` — ошибка; неизвестные *ключи* игнорируются
    (совместимость вперёд). Лимиты: глубина ≤ 32, узлов ≤ 10 000.
15. **Ошибки валидации — списком с путями** (2026-10-26, M3):
    `ScenarioValidationError.issues` (`path` вида `nodes[2].children[0].x`,
    до 50 ошибок). CLI печатает их понятным текстом, в M4 это даст подсветку
    конкретного блока.
16. **Стабильные `id` узлов** (2026-10-26, M3): необязательный `id`
    (уникальный в сценарии) сохраняется в IR; интерпретатор сообщает текущий
    узел через `on_node(node, path)` — в M4 станет подсветкой выполнения
    без изменения формата.
17. **Остановка внутри интерпретатора** (2026-10-26, M3): `delay` реализован
    через `Event.wait` и прерывается мгновенно; стоп проверяется перед каждым
    узлом и итерацией; `FailsafeTriggered` проходит наружу без обёртки
    и превращается в `StopReason.FAILSAFE` общим воркером.
18. **Blockly 13.4.0 — pinned vendor без CDN** (2026-10-27, M4):
    в `resources/blockly/` лежат только core, стандартные блоки, русские
    сообщения, media и LICENSE (Apache-2.0). Генераторы кода не нужны:
    IR собирается сериализацией workspace. Обновление версии — только
    `scripts/vendor_blockly.py`; вендоренные файлы не редактируются.
    Страница работает с `file://` без интернета.
19. **Гибридный `.acl.json`** (2026-10-27, M4): IR (`version`, `name`, `nodes`)
    — источник истины для исполнения; необязательное
    `editor: {"kind": "blockly", "workspace": ...}` хранит точное состояние
    холста (позиции, отключённые блоки). Схема IR игнорирует неизвестные
    ключи, поэтому CLI и файлы M3 совместимы. При открытии workspace
    сверяется с `nodes`; при расхождении блоки строятся из IR, а пользователь
    видит пояснение.
20. **Единая валидация и подсветка ошибок** (2026-10-27, M4): транслятор
    Blockly → IR не дублирует диапазоны — он собирает IR с `id` узлов = `id`
    блоков и вызывает `scenario_from_mapping`. Ошибки схемы сопоставляются
    с блоками по пути (`nodes[2].children[0].x` → `id`), неизвестный тип
    блока даёт `BlocklyIssue` сразу с `id`. В редакторе это `setWarningText`
    и центрирование на первом проблемном блоке.
21. **`sequence` разворачивается; hat-блок и `if` не выводятся**
    (2026-10-27, M4): `sequence` семантически равен стеку, поэтому при
    обратной трансляции разворачивается с сохранением `id` детей; отдельного
    блока «группа» нет. Блок «когда сценарий запущен» не вводится — IR не
    событийный, корневой стек выполняется сверху вниз. Узел `if` в палитру
    M4 не попадает (интерпретатор пока отказывает).
22. **QWebChannel и HTML-тулбар** (2026-10-27, M4): JS → Python — слоты
    `run/stop/save/open/new_document/ready/log`; Python → JS — сигналы
    (`scenario_loaded`, `node_started`, `step_done`, `run_finished`,
    `issues_found`, `status_changed`, `document_saved`, `running_changed`).
    Тулбар живёт в HTML, чтобы undo/redo и dirty-флаг работали напрямую
    с Blockly. Диалоги файлов — в bridge (GUI-поток), с инъекцией для тестов;
    JS-код из workspace не исполняется.
23. **Контекстные хоткеи и защита от двух прогонов** (2026-10-27, M4):
    `F5` запускает активный режим (редактор → сценарий, иначе клики),
    `F6` всегда останавливает и клики, и сценарий. Запуск второго режима
    при работающем первом отклоняется с подсказкой — иначе два потока
    одновременно двигали бы единственный курсор Windows.
24. **Ленивая загрузка WebEngine и чистое завершение** (2026-10-27, M4):
    страница редактора создаётся при первом показе вкладки (быстрее старт,
    меньше памяти) и только в GUI-потоке. На выходе `EditorView.shutdown()`
    и `application.run()` принудительно уничтожают webview до `QApplication`:
    иначе QtWebEngine на Windows падает после завершения процесса. Ошибки бэкенда
    оборачиваются в `ScenarioRuntimeError` с путём узла и `__cause__`.

## 4. Правила кодинга

- Python 3.11+, **type hints везде** (включая возвращаемые значения).
- Форматирование: **ruff** (lint + format). Стиль — PEP 8.
- Имена в коде — **на английском**; комментарии, docstrings и документация — **на русском**.
- Docstring обязателен для всех публичных классов/функций/модулей.
- `core/` не импортирует `gui/` и `PySide6` (кроме `QtCore` для сигналов воркера —
  и то только в слое-адаптере).
- Никаких «божественных» классов: файл > ~300 строк — повод разбить.
- Одна фича = одна ветка/коммит; сообщения коммитов в формате `type: subject`
  (feat/fix/docs/refactor/test/chore), на русском или английском — последовательно.
- Конфиг приложения (хоткеи, выбранный бэкенд, тема) — через единый модуль
  настроек с сохранением в JSON в `%APPDATA%`.
- Любой пользовательский ввод (в т.ч. JSON из Blockly) валидируется перед исполнением.
- **`.gitignore` всегда актуален:** добавил инструмент или процесс, порождающий
  артефакты (кэши, сборки, логи, локальные конфиги, пользовательские данные) —
  сразу дополни `.gitignore` соответствующими шаблонами. Случайно попавшие в
  индекс артефакты удаляй через `git rm --cached <путь>`.
- **Вендоренные файлы Blockly не редактируются:** `blockly_compressed.js`,
  `blocks_compressed.js`, `msg/`, `media/` обновляются только через
  `python scripts/vendor_blockly.py` (версия pinned). Наши файлы страницы
  (`index.html`, `blocks.js`, `theme.js`, `editor.js`, `editor.css`) — рядом.

## 5. Глоссарий

- **IR (Intermediate Representation)** — внутренний JSON-формат сценария.
- **IR-узел** — типизированный шаг сценария (`click`, `delay`, `loop`, …).
- **`.acl.json`** — файл сценария ClicKit (IR, версионированный, валидируемый);
  может дополнительно хранить состояние холста в `editor.workspace`.
- **Blockly-JSON** — сериализованное состояние холста Blockly
  (`Blockly.serialization.workspaces.save`), в файле лежит в `editor.workspace`.
- **Бэкенд ввода** — реализация `InputBackend` (pyautogui или pynput).
- **Простой режим** — классический автокликер без блочного редактора.
- **Редактор** — вкладка с Blockly для сборки сценариев.
- **Пикер** — инструмент «наведи и нажми хоткей, чтобы захватить координаты».
