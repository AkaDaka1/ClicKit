# M11 — Безопасность и устойчивость

> План создан 2026-11-01. Статус: 📋 запланировано.
> Зависимости: M7–M10 (сервис, наблюдаемость, инфраструктура, доставка).
> M11 не блокирует первые три вехи: это следующий уровень зрелости.

## 1. Цель

Проверить сервис на прочность и недоверие: зависимости и образы без
известных уязвимостей, артефакты подписаны и имеют SBOM, нагрузка измерена,
данные восстанавливаются из бэкапа, а инцидент разбирается по runbook,
а не «по памяти».

## 2. Критерий готовности

- [ ] Dependabot/Renovate, `pip-audit`, Trivy (образ и IaC), CodeQL и
      gitleaks работают в CI; HIGH/CRITICAL не проходят.
- [ ] SBOM (CycloneDX) публикуется вместе с образом; `cosign` подписывает
      образ, CD проверяет подпись перед деплоем.
- [ ] GitHub Actions запинены по SHA, permissions минимальны, секретов в
      логах и репозитории нет.
- [ ] `SECURITY.md` и лёгкая threat model (STRIDE) описывают границы,
      активы и меры.
- [ ] k6-тест: 100 RPS 10 минут, p95 < 300 мс, ошибок < 0.1%;
      HPA масштабирует; отчёт и графики в `docs/sre/capacity.md`.
- [ ] Capacity-документ: RPS на реплику, CPU/RAM на запрос, лимит соединений
      БД, формула масштабирования, стоимость 1k запросов.
- [ ] Бэкап Postgres ежедневно в S3-совместимое хранилище; восстановление
      в staging проверено; RTO/RPO измерены и записаны.
- [ ] 4 chaos-эксперимента (kill pod, недоступная БД, заполнение диска,
      просроченный сертификат) с наблюдением алертов и runbook.
- [ ] Учебный инцидент: таймлайн, действия по runbook, blameless-постмортем,
      задачи с владельцами.
- [ ] README содержит блок Reliability: SLO, p95, RPS, MTTR, ссылки на
      `docs/sre/` и публичное демо.

## 3. Согласованные параметры

| Параметр | Решение |
|---|---|
| Порог сканера | HIGH/CRITICAL блокируют merge; исключения — только с датой и причиной |
| SBOM | CycloneDX, `syft`; хранится как артефакт и прикреплён к образу |
| Подпись | `cosign` keyless (OIDC GitHub Actions); проверка в CD |
| Нагрузка | k6: smoke 5 VU, load 100 RPS 10 мин, stress до 500 RPS |
| SLO нагрузки | p95 < 300 мс, error rate < 0.1%, без OOM/рестартов |
| Бэкапы | `pg_dump` ежедневно, retention 7 дней + 4 недельных; шифрование |
| RTO/RPO | Цель RTO ≤ 30 мин, RPO ≤ 24 ч; фактические цифры — после drill |
| Chaos | Только staging; окно и откат описаны заранее |
| Инцидент | Учебный, без реальных пользователей; blameless |

### 4.1. Безопасность цепочки поставки

- Dependabot: pip, Docker, GitHub Actions; weekly, grouped.
- `pip-audit -r requirements*.txt`; Trivy image + config; CodeQL Python.
- gitleaks на историю и PR; actions — по commit SHA, `permissions: read-all`
  на уровне workflow, повышение точечно.
- SBOM: `syft <image> -o cyclonedx-json`; `cosign attach sbom` + `cosign sign`.
- Проверка подписи в CD: `cosign verify` с identity/regexp GitHub OIDC.

### 4.2. Нагрузка и capacity

- k6-сценарии с thresholds; запуск против staging по расписанию/вручную.
- Метрики: RPS, p50/p95/p99, error rate, CPU/RAM, соединения БД, рестарты.
- HPA наблюдение: при 100 RPS — сколько реплик, где предел.
- `docs/sre/capacity.md`: измерения, формула, cost per 1k requests, вывод
  «что делать при росте в 10 раз».

### 4.3. Бэкапы и восстановление

- CronJob `pg_dump` → S3-совместимое хранилище; шифрование, retention.
- `restore.sh` разворачивает дамп в отдельную staging-БД, не в prod.
- Drill: измерить время от «данные потеряны» до «сервис читает данные»;
  записать RTO/RPO, gaps.
- Проверка целостности: контрольная сумма дампа, выборочный `SELECT`.

### 4.4. Chaos и инциденты

- `kill pod` → Kubernetes перезапускает, сервис не теряет доступность.
- `DB down` → `/readyz` 503, алерт, понятная ошибка 503, восстановление.
- `disk full` → алерт, отсутствие порчи данных, runbook.
- `cert expired` → алерт за 14 дней, перевыпуск, проверка HTTPS.
- Учебный инцидент: имитация 5xx, таймлайн, runbook, постмортем,
  action items с владельцами и сроками.

## 5. Решения (ADR; итог — в `AI_CONTEXT.md` §3.3)

- **ADR №48 — безопасность как ворота CI, а не разовая проверка.**
  Сканирование, SBOM и подпись встроены в пайплайн; исключения имеют срок.
- **ADR №49 — нагрузка измеряется на staging, а не «в голове».**
  Capacity-документ содержит фактические цифры и ограничения, включая
  стоимость и предел одной реплики.
- **ADR №50 — восстановление проверяется, а не предполагается.**
  Бэкап без drill — это надежда; RTO/RPO фиксируются по факту.

## 8. Чек-лист приёмки

- [ ] Ни один HIGH/CRITICAL не проходит без явного исключения со сроком.
- [ ] Подпись образа проверяется до деплоя; подделка/старый digest отклоняется.
- [ ] Нагрузочный отчёт воспроизводим; понятно, где предел.
- [ ] Восстановление из бэкапа проверено, а не описано.
- [ ] Chaos не сломал staging без возможности вернуться.
- [ ] Постмортем blameless; action items имеют владельцев и сроки.
- [ ] README не обещает больше, чем измерено.

## 9. Риски и меры

| Риск | Мера |
|---|---|
| Сканеры шумят | Порог HIGH/CRITICAL, группировка, исключения с датой |
| Подпись ломает CD | Сначала verify в отдельном job, затем обязательный шаг; fallback с ручным approval |
| Нагрузка роняет staging | Окно, лимиты, HPA, откат; не запускать в prod |
| Бэкап не восстанавливается | Drill в отдельную БД, проверка целостности, RTO/RPO |
| Chaos выходит за staging | Namespace-scope, запрет prod-контекста, чек-лист перед запуском |
